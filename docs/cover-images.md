# 列表封面：加载态、死链与补取

2026-10-24。

**问题**：部分歌单卡片在外面（搜索 / 收藏列表）是空白封面，点进详情却有封面。
第一反应是「列表接口没返回 pic」，实测不是 —— 返回了，但地址本身打不开。

---

## 1. 实测结论

**同一个歌单，列表与详情给的不是同一个文件。**

| 来源 | 示例地址 | 结果 |
| --- | --- | --- |
| 列表（搜索） | `music-file.y.qq.com/..._o.jpg` | 404 |
| 详情（`playlist/info`） | `music-file.y.qq.com/..._56211.jpg` | 200 |

用「周杰伦」搜歌单，143 个结果里 **55 个封面加载失败**。最大一类是
`y.gtimg.cn/..._o.jpg`（38 个）：列表把文件名里的**数字 0 写成了字母 o**，
改成 `_0.jpg` 后 302 到真实图片、200。剩余是零星的第三方 CDN 404 / 400。

> 这些地址来自 QQ 音乐。波点只是把对方歌单的封面地址原样带过来了，坏链在数据源那边。
> 调研只用了两条歌单详情 + 一页搜索，没有再批量探测。

## 2. 处理

### 2.1 能就地修的直接改 URL

`BodianApi.ToHttpUri` 对 `y.gtimg.cn` 且路径含 `_o.jpg` 的地址替换成 `_0.jpg`。
限定域名，避免误伤其它站点。零请求。

### 2.2 修不了的按详情补一次

`Services/PlaylistCoverResolver`：图片失败时用列表项自带的 `id + sourceType`
调一次 `GetPlaylistInfoAsync`，拿详情里的 `pic` 重试。

- 结果按 `(id, source)` 缓存，**失败也缓存**；卡片滚回来不重复请求。
- 同时在途请求限 4 个，避免一屏卡片一起打服务端。
- 只对可见且确实失败的卡片触发；图片正常时没有任何额外请求。
- 列表项的 `sourceType` 是「在哪个列表里看到的」，不等于详情要的 source：
  收藏列表里的个别条目用 `4` 只回空 pic。所以按「它自己的 → `5` → `13`」依次试，
  拿到封面就停；多数条目第一次就成功，只有真正取不到的才多走一两步。

### 2.3 `Controls/CoverImage`

**没有加载态**，与专辑卡片一样：`Source` 给上就直接画，不转圈。

- 图片失败 → 先走 §2.2 补取；仍失败才画占位（音符图标），不留一块空白。
- **不能只看 `ImageOpened` / `ImageFailed`**：容器回收时会把已经解码完的 `BitmapImage`
  挂到新的 `Image` 上，`ImageOpened` 不再触发；迟到的 `ImageFailed` 还可能串到下一项。
  `CoverImageCache` 为每张位图记一份加载结果（成功 / 失败 / 解码中），控件先查结果。
- 补取回来的地址走 `Formats.CoverSource`，仍然经过内存与磁盘两层缓存；
  直接 `new BitmapImage` 会绕过缓存，滚回来重新下一遍。
- 保留 `Motion.SharedCoverKey`，共享封面动画不受影响。

替换范围：搜索页歌单卡片、收藏的歌单卡片、收藏歌单的列表行。其余封面（专辑、歌手、
首页卡片）暂未接入；`CoverImage` 可以直接复用。

## 3. 验证

- 构建 0 错误；离线测试 1691 项通过。
- 搜索「周杰伦」→ 歌单页签：原先空白的卡片应出现封面（大部分经 §2.1 直接显示）。
- 给的两个分享歌单（`96687791` / `100449307`）：卡片先转圈，随后经详情补取显示出封面。
- 断网：卡片不再空白，显示音符占位。
- 滚动列表来回：不重复转圈、不重复请求。
